# Trade-offs and Limitations

This repository now demonstrates a governed SDLC path from intake through CI, test evidence, release-candidate approval, and operations handoff. It is **not production-ready software or a complete production SDLC implementation**. The following gaps are deliberate and must be closed before real production use.

- **Agents do not mutate the orchestrator's own source tree.** The Implementation/Design/Documentation agents write descriptive artifacts (design.md, implementation_notes.md, diff.md, generated_docs.md) into the run's sandboxed `artifacts/` directory rather than live-patching `src/agentic_engineer/url_shortener/`. The one deliberate exception is the **Test agent**, which genuinely executes the real project's pytest suite, so validation evidence is real rather than simulated. Mutating a running system's own source as part of a demo run was judged too risky/circular for a prototype; a production version would target a separate checked-out repository/branch.
- **Copilot is the configured provider by default, with SDK tools disabled.** The adapter passes `available_tools=[]`; Copilot can return text suggestions but cannot invoke the SDK's built-in shell/filesystem tools. A live SDK smoke test has succeeded after CLI authentication, but all product role calls still need quality monitoring and structured output validation before being trusted.
- **CI is a baseline, not a full supply-chain program.** `.github/workflows/ci.yml` runs tests on Python 3.11/3.12, `pip-audit --skip-editable` for third-party packages, and a wheel build. The repository must separately require both matrix checks in branch protection/rulesets for them to block merges. CI does not yet pin third-party actions by full commit SHA, generate an SBOM/provenance attestation, run SAST/secret scanning, enforce coverage thresholds, or sign releases.
- **No change is applied to the target source tree.** The Developer agent proposes changes in artifacts only. A real SDLC implementation needs an isolated target checkout/branch, validated patch format, path-limited patch application, human approval, and post-apply validation.
- **No CD/deployment is implemented.** Release approval creates an `APPROVED_CANDIDATE` manifest with `deployment_state: NOT_DEPLOYED`; it does not authorize deployment. There is no target environment, deployment adapter, progressive rollout, or automatic rollback. Choose a hosting provider/environment and define credentials, secrets, and approval policy before adding CD.
- **Operations is a handoff, not an operating service.** The generated runbook identifies required controls but no production auth, durable/distributed persistence, backups, alerting, dashboards, paging, SLOs, incident integration, or retention enforcement are configured. `/health` currently reports process health only.
- **Retries have no backoff.** A retried task is simply re-queued on the next scheduling pass; there is no exponential backoff/jitter. Acceptable for a prototype where "task" durations are seconds, not a concern at production scale without adjustment.
- **Safe-stop cannot forcibly interrupt an already-running task.** It only prevents new scheduling. Forcibly killing a live subprocess/thread safely is out of scope for this prototype.
- **Persistence is local JSON files + SQLite**, not a distributed datastore. The `URLRepository`/`StateStore` interfaces are narrow enough to swap in Postgres/S3-backed equivalents without touching callers.
- **Concurrency model is a simple bounded thread pool with level-order (batch) scheduling**, not a general event loop / async executor. This keeps the synchronization-barrier semantics trivially correct at the cost of some scheduling flexibility (a task cannot start until its entire DAG "level" has finished, even if its specific dependency finished much earlier).
- **Single bounded repair attempt.** The repair mechanism demonstrates the required "bounded repair/replan" behavior but is deliberately simple (one repair task per failed task, no repair-of-repair chains).
- **Metrics are a single-process, local-file aggregation**, not a time-series store; "prototype measurement" is stated explicitly in every metrics report rather than implying a production SLO.
- **No authentication/authorization** on the URL-shortener API or the CLI — not suitable for public production until added and reviewed.
